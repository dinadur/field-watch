Worth testing

Fork claims B70 prompt reading four to five times faster in llama.cpp

A/B on a spare box

A developer publishing as valarauca has posted a 33-commit branch of llama.cpp's SYCL backend tuned for the Arc Pro B70. On a dense 27B model it reads prompts about four to five times faster than upstream. For B70 owners, prefill (reading the prompt) has been the weak spot: long agent prompts can take minutes to process even when generation speed is fine.

This addresses a problem B70 owners already know. llama.cpp's default SYCL build does its matrix maths in 32-bit floats and never uses the card's XMX matrix units. That is why community guides keep telling people to rebuild with the FP16 option. The branch makes that choice automatically for each card. It also rearranges quantized weights in memory so the GPU can load them without stalling. Finally, it moves more of prefill onto Intel's oneDNN library, which can unpack compressed weights while it multiplies them.

Worth testing

EXL3 on vLLM remains the fast lane for Qwen3.8-27B

0xSero's exl3xpu plugin runs exllamav3's EXL3 quantization on Battlemage inside vLLM. It is now the base the Flash-Next offload work builds on. On one B70 with Qwen3.8-27B at 4 bits per weight and multi-token prediction switched on, the author reports 54-75 tokens/s for a single user. Prefill runs at about 1,500 tokens/s up to 32K tokens. The author's tuned llama.cpp Q4_K_M baseline on the same card does about 25 tokens/s.

The upshot — worth trying if you serve one 27B model. This is the most-measured high-speed route for that model on a single card. It needs the pinned vLLM XPU image and the driver versions listed in the README.

Risk watch

Driver upgrades keep breaking Battlemage, so pin your stack

A compute-runtime bug report, still open, describes an Arc B580 on Fedora 44 that stopped working after a routine upgrade from 26.22 to 26.35. Every Level Zero and OpenCL program aborted at startup. The reporter could only recover by going back to a much older release. It is a B580 report, not a B70 one, but both cards use the same driver stack.

The upshot — regression risk to watch. Hold compute-runtime, IGC and the Level Zero loader at a known-good set. Update them together, and only after a smoke test.

Plan ahead

Qwen3.8-Flash-Next on one B70: two routes, both experimental

Qwen3.8-Flash-Next is far too big for 32 GB of VRAM. Two projects now report it running on a single B70 by keeping only the most-used "experts" (the sub-networks a mixture-of-experts model switches between) on the card and fetching the rest from RAM or disk.

The upshot — worth planning for, not deploying. If you want Flash-Next on one card, Strata's port is the easier experiment. The NVMe recipe needs serious storage and has known correctness bugs. On two cards, check how the layers are split between them before you blame the driver.
