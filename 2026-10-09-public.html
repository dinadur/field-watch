Worth testing

Fork claims up to five times faster prompt reading for llama.cpp on the B70

A/B in a sandbox, don't deploy

Developer valarauca has opened a 33-commit pull request against his own llama.cpp fork that reworks most of the SYCL backend for Xe2 cards. On the B70 he reports Qwen3.8-27B reading a prompt four to five and a half times faster than upstream, plus a big jump in generation speed for some i-quants. Prefill is the slow, painful part of long-context work on this card, so the claim matters.

Context: upstream SYCL has long trailed CUDA and Vulkan on matrix-heavy work. The fork's author found one simple cause. Default builds converted weights to 32-bit floats and ran a matrix multiply that never touched the card's XMX matrix units. In one commit, a default build of an 8B F16 model went from 1,066 to 4,975 tok/s on a 512-token prompt. Other commits change how quantized weights are laid out in memory so the GPU can read them without stalls, and they send more prefill work through oneDNN.

“If prefill is your bottleneck, build the branch next to your current binary and compare speed and output (perplexity or KL divergence) on your own quant.”The upshot — A/B in a sandbox, don't deploy

Worth testing

Recipe fits Qwen3.8-Flash-Next on one B70 by streaming experts from NVMe

sybil-solutions has published measured results for running Qwen3.8-Flash-Next, a 180B-class mixture-of-experts model, from one 32 GB B70 with host RAM capped at 32 GB. The routed experts live on NVMe. The end-to-end figures, measured on 2026-10-06, are about 24 tok/s decode and 1,050-1,260 tok/s prefill at 8K and 32K prompts.

The upshot — worth planning for, not trying casually. If you already have very fast striped NVMe and want Flash-Next on one card, this is the most complete public recipe so far. Everyone else should wait for the race fix and for someone to reproduce it on different storage.

Risk watch

Report: newest Intel compute runtime crashes at startup on a Battlemage card

On 3 October, a Fedora 44 user filed a bug saying that upgrading Intel's compute runtime from 26.22 to 26.35 made every Level Zero and OpenCL program abort at initialization on an Arc B580. That includes basic tools like sycl-ls and clinfo. Rolling the whole stack back to 25.48 fixed it. The 26.22 packages had already been dropped from the distro repositories, so going back meant skipping several releases.

The upshot — regression risk to watch. If your distro auto-updates the Intel compute stack, hold it until you've tested the new version on your card, and keep a known-good version available locally rather than relying on the repo.

Plan ahead

llama.cpp v0.6.0 adds Flash-Next speculative decoding and SYCL sparse attention

The llama.cpp project tagged v0.6.0 on 5 October. For B70 owners, three changes stand out. "High-quality" support for the Qwen4Exp architecture behind Qwen3.8-Flash-Next now includes MTP speculative decoding, where the model's own draft head proposes tokens. ggml v0.26.0 adds sparse flash-attention kernels for SYCL alongside Vulkan and Metal. And there is native support for Cloudflare's Clef decision models.

The upshot — plan an upgrade, benchmark first. If you run Flash-Next GGUFs, test MTP on your card before assuming the Spark speedup carries over. Re-check any saved sessions after upgrading because of the format bump.
