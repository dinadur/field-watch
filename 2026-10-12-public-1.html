Fork of llama.cpp's SYCL backend makes B70 prompt reading up to five times faster

A/B now, on a side build

A developer publishing as valarauca has opened a 33-commit branch of llama.cpp tuned specifically for the Arc Pro B70. It is the largest single jump in SYCL prompt processing (prefill, how fast the model reads your prompt) reported for this card. On Qwen3.8-27B at Q4_0 the author measures about 1,370 tokens per second reading a 512-token prompt, against about 250 on mainline: roughly five and a half times faster. For anyone running long-context agent work on one card, prefill is usually the main wait, so this is the change that matters most this week.

Prefill has long been the B70's weak spot under llama.cpp. Benchmarkers have known for months that the default build leaves much of the card's matrix hardware idle. The author found the root cause. Default builds converted quantized weights to 32-bit floats and ran a matrix multiply that never touched the XMX units, Intel's matrix engines. The branch now chooses 16-bit math per device automatically. On its own, that change raised an 8B model's prefill from about 1,070 to about 4,980 tok/s. Most of the remaining commits reorganise how quantized weights sit in memory, so that Xe2 cards can load them without stalls.

Decode (generating tokens) mostly stays where it was for common quants, about 27.6 tok/s on the 27B at Q4_0. The exception is the IQ quant families, which the author reworked heavily. Unsloth's UD-IQ4_XS on the 27B rises from about 16.6 to 26 tok/s, which brings it level with Q4_0. On Qwen3-Coder-30B-A3B, prefill improves by 40-60%.

The branch also fixes several correctness bugs, and these matter even if speed doesn't. Q4_0 and related formats drifted measurably from the CPU reference. A precision hint was ignored, which could turn activations into NaNs. A flash-attention path read the wrong batch's KV cache. The author checked each change with KL-divergence comparisons against the CPU.

Some caveats apply. The pull request targets the author's own fork, not upstream. It has no reviews. Every number comes from the author's single machine. The author also says the tensor-math changes were written autonomously by an AI model in a benchmark loop, and one commit was later reverted when its claimed gain turned out to be noise. The PR was opened on October 4, a day before this window, and was still open and unmerged at press time.

Under the hood. The branch is feature/intel on valarauca/llama.cpp. The automatic 16-bit choice can be forced with GGML_SYCL_FP16_GEMM=0/1, and the oneDNN weight-decompression prefill path can be switched off with GGML_SYCL_DNNL_WDECOMP=0 if results look wrong. SYCL graphs (GGML_SYCL_ENABLE_GRAPH=1) remain opt-in. The author reports they no longer slow decode down.

The upshot — A/B now, on a side build. If you run the 27B or IQ-quant GGUFs on llama.cpp SYCL, build this branch next to your current one. Compare prefill and output quality on your own prompts. Keep mainline for production until someone else reproduces the numbers or the work goes upstream.
Sources: valarauca/llama.cpp PR #1
