Worth testing

Fork of llama.cpp's SYCL backend makes B70 prompt reading up to five times faster

A/B now, on a side build

A developer publishing as valarauca has opened a 33-commit branch of llama.cpp tuned specifically for the Arc Pro B70. It is the largest single jump in SYCL prompt processing (prefill, how fast the model reads your prompt) reported for this card. On Qwen3.8-27B at Q4_0 the author measures about 1,370 tokens per second reading a 512-token prompt, against about 250 on mainline: roughly five and a half times faster. For anyone running long-context agent work on one card, prefill is usually the main wait, so this is the change that matters most this week.

Prefill has long been the B70's weak spot under llama.cpp. Benchmarkers have known for months that the default build leaves much of the card's matrix hardware idle. The author found the root cause. Default builds converted quantized weights to 32-bit floats and ran a matrix multiply that never touched the XMX units, Intel's matrix engines. The branch now chooses 16-bit math per device automatically. On its own, that change raised an 8B model's prefill from about 1,070 to about 4,980 tok/s. Most of the remaining commits reorganise how quantized weights sit in memory, so that Xe2 cards can load them without stalls.

Strata's Arc port ships in 0.1.39, but nobody has run it on an Arc yet

Strata is the popular one-click engine for running Flash-Next on consumer GPUs, and its 0.1.39 release now includes an experimental Intel Arc build. The port was written by contributor maxfridbe and moved onto the 0.1.39 engine sources. For B70 owners it is the simplest-looking way to run Flash-Next variants. Even so, the maintainers say plainly that they have no Intel GPU. They compiled the port and ran its kernel tests on a CPU, where 14 of 25 pass. The 0.1.39 build itself has not been run on Arc hardware by anyone.

The Arc numbers so far come from community testers on earlier versions. On one B70 the port author reported 70-78 tok/s decode with the Coder IQ1_M variant and 51-64 tok/s with IQ2_XS. A two-B70 user reported 66 tok/s on full Flash-Next at IQ3_XXS. A B580 tester on WSL2 saw device loss.

The upshot — Worth trying if you like to tinker, and worth reporting back. If you build 0.1.39 on a B70, you will be among the first to run it. The maintainers ask for card, driver, oneAPI version and logs.

Worth testing

Dual-B70 vLLM gets graph capture working at TP=2

On two-B70 machines, splitting one model across both cards with tensor parallelism (TP=2) has been held back by a plumbing problem. oneCCL, Intel's communication library, could not be recorded into an XPU graph. That forced TP=2 to run in slower eager mode while single-card runs did not. Developer recutita built a custom peer-to-peer all-reduce over Level Zero IPC to get around it. On Qwen3.8-27B GPTQ INT4, that path measured about 55 tok/s at TP=2 against about 32 on the best single-card run, and about 85 against 50 with MTP speculative decoding.

The upshot — Worth trying if you run two cards on vLLM. If you skipped TP=2 because it ran eager and lost to one card, re-test with graph capture and the oneCCL thresholds above. Single-card users have nothing to do.

Risk watch

Latest Intel compute runtime crashes a Battlemage card at startup on Fedora

A Fedora 44 user reports that upgrading Intel's compute runtime from 26.22 to 26.35.39758.11 broke every GPU compute program on their machine. The upgrade came in through a routine package update, and it took down Level Zero, OpenCL and SYCL. Even Intel's hello-world sample aborts during driver startup, before any work is submitted. The kernel log shows nothing wrong. The only fix the reporter found was to roll back to 25.48, because 26.22 is no longer in Fedora's repositories.

The upshot — A risk to avoid. If your distro is about to move you to compute-runtime 26.35, pin your current version until this issue is resolved or someone confirms the B70 is unaffected. Keep a known-good package set where you can reinstall it.

Plan ahead

One B70 serves Qwen3.8-Flash-Next by streaming experts from NVMe

A research repo from sybil-solutions shows Qwen3.8-Flash-Next running on a single Arc Pro B70 with host RAM capped at 32 GB. Flash-Next is Qwen's 177-billion-parameter mixture-of-experts preview of its Qwen4 architecture. The run uses a 3.05-bit EXL3 quant, and most of the model's experts stay on NVMe. In a full end-to-end run on October 6, the author measured about 24 tok/s decode for one user and about 1,050-1,260 tok/s prompt reading at 8K and 32K context. That puts a model of this size within reach of a one-card box, at speeds you could actually use.

The upshot — Plan for it, don't deploy it. This is the most concrete evidence yet that a single B70 can serve Flash-Next. Wait for the write-back race fix before you trust long runs, and budget for very fast multi-drive NVMe if you want these numbers.
